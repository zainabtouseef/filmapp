WHAT THIS PROJECT DOES
----------------------

Dep-Hallucinator reads dependency files such as requirements.txt, package.json,
and Maven pom.xml. It checks whether package names exist in their official registry
and applies name-based heuristics. Each package receives one result:

- LOW: no important warning was found by this scan
- MEDIUM: suspicious enough to review
- HIGH: strong warning; do not install without investigation
- CRITICAL: package is missing, explicitly blocked, or otherwise highly dangerous
- ERROR: the scanner could not complete the check; this is unknown, not safe

The scanner helps with dependency-confusion and hallucinated-package detection.
It is not a complete malware scanner and a LOW result is not a security guarantee.


MODIFICATION 1 — PERSISTENT ALLOWLIST AND DENYLIST
--------------------------------------------------

Easy explanation:
The old add/remove commands changed a list only in the current Python process. As soon
as that command ended, a new process rebuilt the default lists and the user's entry was
gone. The modification saves the lists to JSON and reloads them next time.

Detailed flow:
1. PackageListManager selects ~/.config/dep-hallucinator as its configuration folder.
2. _read_entries reads allowlist.json or denylist.json and recreates typed entries.
3. If a saved file exists and is valid, it replaces the corresponding default list.
4. Add/remove changes the in-memory list and immediately calls _write_entries.
5. _write_entries writes a .tmp file first and then replaces the real file. This reduces
   the chance of leaving a half-written JSON file if writing is interrupted.
6. Invalid or missing saved JSON falls back safely instead of crashing startup.

Exact files and places:
- src/dep_hallucinator/package_lists.py:5 — # modification1 marker
- package_lists.py:96–150 — JSON read, atomic write, and startup reload
- package_lists.py:274–339 — save after allowlist/denylist add or remove
- tests/test_package_lists.py:4–39 — two persistence tests


MODIFICATION 2 — SECURE MAVEN XML PARSING
-----------------------------------------

Easy explanation:
A pom.xml is input supplied to the scanner, so it must not be trusted. A specially made
XML file can define an external entity that points to a local file. An unsafe parser may
expand that entity and expose the local contents. This is called XML External Entity,
or XXE, injection. The modification uses defusedxml, which rejects dangerous XML
features before dependency extraction begins.

Detailed flow:
1. pyproject.toml installs defusedxml as a production dependency.
2. parsers.py imports defusedxml.ElementTree under the existing ET name, so the normal
   Maven parsing code remains small and readable.
3. ET.fromstring reads normal Maven XML exactly where the old parser was used.
4. A DOCTYPE/external-entity attempt raises DefusedXmlException.
5. The scanner logs the parsing event and raises a clear ValueError containing
   “Unsafe XML content”; it never expands the external entity.
6. The security test creates a harmless demonstration reference to file:///etc/passwd.
   It checks only that parsing is blocked; it does not read or print that file.

Exact files and places:
- src/dep_hallucinator/parsers.py:8–10 — # modification2 and safe imports
- parsers.py:780–833 — parse with defusedxml and handle blocked input
- pyproject.toml:35 — defusedxml>=0.7.1 dependency
- tests/test_parser_security.py:6–25 — malicious external-entity rejection test

Why this is a meaningful student-level contribution:
It closes a real input-parsing risk with a standard security library, changes only a
small part of the parser, preserves valid Maven behavior, and has a focused regression
test that explains the security property.

STEP 20 — UNDERSTAND THE CLASSROOM SAFE PERCENTAGE
--------------------------------------------------

Dep-Hallucinator gives every package a risk level. It does not define one official
whole-project safety percentage. For a simple classroom comparison, use:

safe percentage = number of LOW findings / total findings × 100

Only LOW is counted as safe. MEDIUM, HIGH, CRITICAL, and ERROR all need review.
An ERROR often means the registry could not be reached, so never count ERROR as safe.
This percentage summarizes the scan; it does not guarantee that code is secure.
